## 1. 问题的本质：模型幻觉从何而来

### 1.1 幻觉的三种类型

| 类型 | 表现 | 根因 | 实例 |
|------|------|------|------|
| **事实性幻觉** | 编造不存在的事实 | 模型训练数据不包含企业私有知识 | 问「云帆商城退款时效」，答「行业通用 7 天」（实际是 15 天） |
| **口径性幻觉** | 给出多个互相矛盾的答案 | 同一概念在不同语境下有不同定义，模型无法判断哪个是「我们的」定义 | 问「退款率怎么算」，罗列 5 种公式，不说哪个是公司官方口径 |
| **逻辑性幻觉** | 推理过程看似合理但结论错误 | 模型缺乏业务约束知识，无法判断哪些组合是合法的 | 问「拆封的美妆能无理由退吗」，答「可以，7天无理由适用所有商品」（忽略了美妆拆封的例外规则） |

### 1.2 幻觉的本质原因

**核心问题**：LLM 是概率模型，不是知识数据库。它的输出是基于训练数据的统计规律，而不是基于事实的逻辑推理。

```
用户问：「云帆商城退款率怎么算？」

LLM 内部过程：
1. 检索训练数据中关于「退款率」的所有内容
2. 按概率分布生成最「像」答案的文本
3. 输出：「退款率 = 退款订单数 / 总订单数」（行业通用公式）

问题：
- 模型不知道「云帆商城」的官方口径是「售后退款成功订单数 / 总订单数（自然月）」
- 模型不知道取数位置是 aftersale.status='REFUND_SUCCESS'
- 模型不知道「退货率」和「退款率」是两个不同概念，需要主动提醒
```

**结论**：裸 LLM 的幻觉不是 bug，是设计行为——它本来就没有你的私有知识。

## 2. 为什么本体能解决幻觉：四个核心机制

### 2.1 机制一：证据锚定（Evidence Anchoring）

**原理**：本体要求每条知识必须关联到原始证据，没有证据的知识不被接受。

```
本体四件套之一：证据（Evidence）
- 每条知识必须指回原文段落
- 抄原文而非转述
- 没有证据的知识 = 模型编造的知识
```

**防幻觉效果**：
- ✅ LLM 回答时必须引用本体中的证据
- ✅ 用户可回溯原文核实
- ✅ 无法引用证据的回答被拦截

**实例**：
```
问：「退款申请有时效限制吗？」

裸 LLM 回答：
「一般有 7 天、15 天、30 天等，具体看平台政策。」
→ 幻觉：罗列多个可能性，不说哪个是云帆的规定

接本体后回答：
「退款申请须在订单完成后 15 天内发起。
 证据：《云帆商城产品手册 v3.2》§2.2 原文」
→ 可信：有明确证据，可回溯核实
```

---

### 2.2 机制二：约束锁定（Constraint Locking）

**原理**：本体通过白名单和 domain/range 定义业务约束，把开放作文改选择题。

```
本体的三层纪律：
1. 白名单：只允许预定义的关系类型（如 belongsToSpu、inCategory）
2. domain/range：每种关系限定主语宾语类型
3. 约束：不能违反的业务规则（如「生鲜类目仅支持质量退货」）
```

**防幻觉效果**：
- ✅ LLM 不能发明本体中不存在的概念或关系
- ✅ 违反约束的回答被拦截
- ✅ 把「可能是什么」收窄到「必须是什么」

**实例**：
```
问：「Apple 和 APPLE 是两个品牌吗？」

裸 LLM 回答：
「可能是同一个品牌的大小写差异，也可能是不同品牌。」
→ 幻觉：给出模糊答案，不做判断

接本体后回答：
「Apple 和 APPLE 是同一品牌的不同写法，已在本体中统一为 brand_id='apple'。
 证据：品牌别名表 v1.2」
→ 可信：本体已做消歧，有明确结论
```

---

### 2.3 机制三：口径统一（Terminology Unification）

**原理**：本体为每个业务概念提供唯一定义，消除歧义。

```
本体术语定义句式：
上位类 + 区分特征 + 区别于易混词

例：
「售后单：售后域中买家发起退款/退货/换货请求的最小记录单元；
 区别于订单——订单是交易行为，售后单是服务请求」
```

**防幻觉效果**：
- ✅ LLM 必须使用本体中的标准术语
- ✅ 同一概念不会有多重解释
- ✅ 易混概念被显式区分

**实例**：
```
问：「退款率和退货率是一回事吗？」

裸 LLM 回答：
「退款率和退货率都是衡量售后情况的指标...」（含糊其辞）
→ 幻觉：不区分两个概念

接本体后回答：
「不是一回事。
 - 退款率 = 售后退款成功订单数 / 总订单数（自然月）
 - 退货率 = 实物退货订单数 / 总订单数（自然月）
 退款包含仅退款和退货退款，退货仅指实物退回。
 证据：《产品手册 v3.2》§4.1 + §4.2」
→ 可信：概念清晰区分，有明确定义和证据
```

---

### 2.4 机制四：路径推理（Path Reasoning）

**原理**：本体将知识组织为图结构，支持多跳推理，每一步都有证据支撑。

```
本体图结构：
节点 = 术语（SPU、SKU、类目、政策...）
边 = 关系（belongsToSpu、inCategory、适用于、例外于...）
约束 = 业务规则（挂在边上）
证据 = 出处（挂在节点或边上）
```

**防幻觉效果**：
- ✅ 推理路径可追溯
- ✅ 每一步都有证据
- ✅ 复杂问题可分解为多步查询

**实例**：
```
问：「拆封的美妆产品过敏了能退吗？」

裸 LLM 回答：
「美妆产品拆封后一般不支持 7 天无理由退货，但如果是质量问题或过敏，可以走特殊通道...」
→ 幻觉：含糊其辞，不给确定答案

接本体后回答（路径推理）：
「可以退，走质量退货通道。
 推理路径：
 1. 美妆类目 -[例外于]-> 7天无理由政策（拆封不支持）
 2. 美妆类目 -[适用于]-> 质量退货通道
 3. 过敏 -[属于]-> 质量问题
 4. 质量退货通道 -[不受限于]-> 7天窗口
 结论：拆封不支持无理由，但过敏属质量问题，走质量通道，不受 7 天限制。
 证据：SOP03#P1 + SOP07#P1」
→ 可信：推理路径清晰，每步有证据
```

## 3. 怎么解决：本体的五层防幻觉架构

### 3.1 架构总览

```
┌─────────────────────────────────────────────────────────┐
│  第五层：进化治理层                                        │
│  - 查询轨迹记录 → 诊断 → 补丁 → 验证 → 发布              │
│  - 持续发现新幻觉模式，持续修补                             │
└─────────────────────────────────────────────────────────┘
                          ↑
┌─────────────────────────────────────────────────────────┐
│  第四层：完备性闸门层                                      │
│  - 合法性检查：符号是否在白名单内                          │
│  - 完备性检查：用户条件是否都在查询中体现                   │
│  - 拦截无法验证的回答，反问用户补充                         │
└─────────────────────────────────────────────────────────┘
                          ↑
┌─────────────────────────────────────────────────────────┐
│  第三层：知识蒸馏层                                        │
│  - LLM 从文档中抽取知识 → candidates.jsonl               │

                          ↑

│  - 人写的术语表                                           │
│  - 存量业务文档（手册/SOP/制度/复盘/决策）                 │
│  - 问答日志 qa_log（定域蒸馏）                             │
└─────────────────────────────────────────────────────────┘
```

### 3.2 第一层：知识原料层——幻觉的源头治理

**核心原则**：垃圾进，垃圾出。如果原料本身就有幻觉，本体无法拯救。

**原料类型与质量控制**：

| 原料类型 | 幻觉风险 | 控制手段 |
|---------|---------|---------|
| 人写的术语表 | 低（人工定义） | 定义句式统一：上位类 + 区分特征 + 区别于易混词 |
| 存量业务文档 | 中（可能前后矛盾） | G6 冲突检测：时效冲突/条件冲突/真冲突，三分法处理 |
| 问答日志 qa_log | 低（真实问题流） | 定域蒸馏：高频问题决定优先蒸馏哪个域 |

**关键纪律**：
- ✅ 围绕真实问题流构建，不从文档目录全量归纳
- ✅ 文档矛盾必须显式标注，不能默默选一个
- ✅ 术语定义必须人工审核，LLM 不能自行创造

---

### 3.3 第二层：本体建模层——幻觉的结构化约束

**本体四件套**：

```
① 术语（Term）
   - 概念节点，定义句式统一
   - 例：「售后单：售后域中买家发起退款请求的最小记录单元；区别于订单」

② 关系（Relation）
   - 带方向的边，必须走白名单
   - 例：belongsToSpu(SKU→SPU)、inCategory(SPU→类目)

③ 约束（Constraint）
   - 不能违反的业务规则
   - 例：「退款申请须在订单完成后15天内发起」

④ 证据（Evidence）
   - 知识的出处，最关键
   - 例：「15天」→《产品手册 v3.2》§2.2 原文
```

**防幻觉机制**：

| 构件 | 防什么幻觉 | 怎么防 |
|------|-----------|--------|
| 术语 | 口径性幻觉 | 同一概念唯一定义，消除歧义 |
| 关系 | 逻辑性幻觉 | 白名单锁定合法关系，不能发明新关系 |
| 约束 | 事实性幻觉 | 业务规则显式化，违反约束的回答被拦截 |
| 证据 | 所有幻觉 | 每条知识必须指回原文，无法引用的被拒绝 |

**双格式宪法**：
- schema.ttl（语义层）：机器可读的语义声明
- schema.json（校验层）：数据落库前的结构校验
- 铁律：英文键一字不差，改一处必须同步另一处

---

### 3.4 第三层：知识蒸馏层——幻觉的自动化过滤

**七道闸门**：

```
G1 JSON合法 → G2 白名单 → G3 实体对齐 → G4 属性归一 → G5 去重 → G6 冲突检测 → G7 置信分级
```

**各闸门防幻觉作用**：

| 闸门 | 拦截对象 | 防什么幻觉 |
|------|---------|-----------|
| G1 | LLM 输出解析失败 | 防止格式错误的知识进入 |
| G2 | AI 自创关系（头号 bug） | 防止 LLM 发明本体中不存在的概念 |
| G3 | 两端实体不在术语表 | 防止术语漂移（Apple/APPLE/apple 统一） |
| G4 | 单位/格式混乱 | 防止口径不一致（1.5L vs 1500ml） |
| G5 | 重复三元组 | 防止知识冗余 |
| G6 | 同主谓不同宾 | 防止文档矛盾导致的逻辑冲突 |
| G7 | 低置信候选 | 防止不确定的知识污染本体 |

**关键纪律**：
- ✅ 宁可拒绝，不可污染
- ✅ 被拦 ≠ 判死刑，进待确认队列，人裁决后重新过闸
- ✅ 质量日报 = 免费体检，哪个闸门拦截率高就修哪一层

---

### 3.5 第四层：完备性闸门层——幻觉的最后一道防线

**核心原则**：宁可反问，不可降智。

**两个检查**：

| 检查类型 | 内容 | 防什么幻觉 |
|---------|------|-----------|
| **合法性检查** | 用的符号是否都在白名单内 | 防止 LLM 使用本体中不存在的概念 |
| **完备性检查** | 用户问题里的条件是否都在查询中体现 | 防止 LLM 遗漏关键约束 |

**判定标准**：
- 用户点选过的硬约束 100% 必须落进查询
- 自然语言命中的 70% 须覆盖
- 不满足 → 拦截回答，反问用户补充

**实例**：
```
用户问：「华东区上个月卖得最好的 10 个商品」

LLM 生成查询草案：
SELECT product, sales FROM orders WHERE region='华东' AND month='上月' ORDER BY sales DESC LIMIT 10

完备性检查：
✅ region='华东' → 命中
✅ month='上月' → 命中
✅ ORDER BY sales DESC → 命中
✅ LIMIT 10 → 命中
→ 通过，执行查询

如果用户问：「华东区卖得最好的商品」

LLM 生成查询草案：
SELECT product, sales FROM orders WHERE region='华东' ORDER BY sales DESC

完备性检查：
✅ region='华东' → 命中
❓ 「最好」→ 没有明确数量（Top 几？）
→ 拦截，反问用户：「请问您想看 Top 几的商品？」
```

---

### 3.6 第五层：进化治理层——幻觉的持续修补

**核心原则**：本体是活系统，不是一次性工程。

**六步进化循环**：

```
建 v0 → 使用攒轨迹（30任务/7天触发） → 诊断（找重复 miss 模式）
→ 归因（内容层/工具层/模式层） → 单点补丁（只改一处）
→ 同条件验证（含没见过的新问题） → 赢了才发布（旧版永留可回滚）
```

**三条铁律**：
1. 没过验证的改动，永远不配正式版本号
2. 验证必须用没参与建库的问题
3. 同条件对比，输了就不发布

**补丁回流机制**：
- 进化产出的补丁不直接改库
- 回到候选池重新过七道闸门
- 没有「进化豁免权」，改动一律平等受检

**防幻觉效果**：
- ✅ 持续发现新幻觉模式
- ✅ 持续修补本体
- ✅ 版本化管理，可回滚
- ✅ 同一个坑不踩两次

## 4. 实战对比：接本体前后的幻觉率变化

### 4.1 案例一：退款率口径

**问**：「云帆商城退款率怎么算？」

**裸 LLM 回答**：
```
退款率 = 退款订单数 / 总订单数

不同平台可能有不同口径，常见的有：
- 仅退款订单 / 总订单
- 退款成功订单 / 总订单
- 退款金额 / 总销售额

建议根据您的业务场景选择合适的口径。
```

**幻觉分析**：
- ❌ 罗列多个公式，不说哪个是云帆的官方口径
- ❌ 没有证据支撑
- ❌ 用户无法判断哪个是对的

**接本体后回答**：
```
云帆商城官方口径：
退款率 = 售后退款成功订单数 / 总订单数（自然月）

取数位置：aftersale.status='REFUND_SUCCESS'

注意：退货率 ≠ 退款率
- 退货率 = 实物退货订单数 / 总订单数
- 退款包含仅退款和退货退款

证据：《云帆商城产品手册 v3.2》§4.1
```

**防幻觉效果**：
- ✅ 给出唯一官方口径
- ✅ 明确取数位置
- ✅ 主动区分易混概念
- ✅ 有证据可回溯

---

### 4.2 案例二：美妆退货政策

**问**：「拆封的美妆产品能无理由退吗？」

**裸 LLM 回答**：
```
根据《消费者权益保护法》，7天无理由退货适用于大部分商品。
但美妆产品属于特殊商品，拆封后可能影响二次销售，部分平台不支持无理由退货。
建议您查看具体平台的退货政策或联系客服确认。
```

**幻觉分析**：
- ❌ 含糊其辞，不给确定答案
- ❌ 把问题推给用户自己查
- ❌ 没有云帆的具体规定

**接本体后回答**：
```
不可以。

推理路径：
1. 美妆类目 -[例外于]-> 7天无理由政策（拆封不支持）
2. 但：美妆类目 -[适用于]-> 质量退货通道
3. 如果是过敏等质量问题，可走质量退货通道，不受 7 天限制

结论：
- 拆封不支持无理由退货
- 过敏属质量问题，走质量通道，可退

证据：SOP03#P1 + SOP07#P1
```

**防幻觉效果**：
- ✅ 给出明确答案（不可以）
- ✅ 区分无理由退货和质量退货
- ✅ 推理路径清晰
- ✅ 有证据可回溯

---

### 4.3 案例三：品牌消歧

**问**：「Apple 和 APPLE 是两个品牌吗？」

**裸 LLM 回答**：
```
Apple 和 APPLE 可能是同一个品牌的大小写差异，也可能是不同的品牌。
在电商场景中，通常建议统一品牌名称以避免混淆。
```

**幻觉分析**：
- ❌ 不给确定答案
- ❌ 把判断推给用户

**接本体后回答**：
```
是同一品牌。

本体中已统一为 brand_id='apple'，别名表记录：
- Apple
- APPLE
- apple

证据：品牌别名表 v1.2 + data_audit.py 体检报告
```

**防幻觉效果**：
- ✅ 给出确定答案（是同一品牌）
- ✅ 说明本体中的处理方式
- ✅ 有证据可回溯

## 5. 本体的边界：什么幻觉本体解决不了

### 5.1 本体能解决的幻觉

| 幻觉类型 | 本体解决方案 | 效果 |
|---------|-------------|------|
| 事实性幻觉（私有知识） | 证据锚定 | ✅ 完全解决 |
| 口径性幻觉（多重定义） | 术语统一 + 约束锁定 | ✅ 完全解决 |
| 逻辑性幻觉（违反约束） | domain/range + 完备性闸门 | ✅ 完全解决 |
| 推理幻觉（多跳错误） | 路径推理 + 证据链 | ✅ 大部分解决 |

### 5.2 本体解决不了的幻觉

| 幻觉类型 | 为什么解决不了 | 替代方案 |
|---------|---------------|---------|
| **常识性幻觉** | 本体只包含业务知识，不包含通用常识 | RAG 检索外部知识库 |
| **时效性幻觉** | 本体更新滞后于业务变化 | 进化治理层持续修补 |
| **开放性幻觉** | 本体无法覆盖所有可能的问题 | 完备性闸门拦截，反问用户 |
| **创造性幻觉** | LLM 可能发明本体中不存在的概念 | 七道闸门过滤 + 人工抽检 |

### 5.3 本体的成本与收益权衡

**成本**：
- 人工建模成本：术语表初建 30 天
- 持续维护成本：进化治理层持续运营
- 学习曲线：团队需要掌握本体建模方法

**收益**：
- 幻觉率下降 50-90%
- 用户满意度提升 55%
- Token 成本节省 20%
- 任务轮次减少 42%

**判断标准**：
- ✅ 有持续的问题流 + 有重复答错的模式 → 值得建本体
- ❌ 一次性问答 + 无重复模式 → 不需要建本体，用 RAG 即可

## 6. 落地建议：分阶段构建防幻觉体系

### 6.1 Phase 1：快速见效（1-2 周）

**目标**：解决 80% 的事实性幻觉

**行动**：
1. 梳理高频问题 Top 20
2. 从业务文档中抽取这 20 个问题的答案 + 证据
3. 构建最小术语表（10-20 个核心概念）
4. 在 prompt 中注入这些术语和证据

**预期效果**：
- 高频问题的幻觉率下降 80%
- 用户满意度显著提升

**关键纪律**：
- ✅ 不要追求完美，先把 v0 建起来
- ✅ 初始静态字典已贡献大部分收益

---

### 6.2 Phase 2：系统化（1-2 月）

**目标**：解决口径性幻觉 + 逻辑性幻觉

**行动**：
1. 构建完整本体（schema.ttl + schema.json）
2. 上线七道闸门（G1-G7）
3. 接入图数据库（Neo4j）
4. 实现路径推理

**预期效果**：
- 口径性幻觉完全解决
- 逻辑性幻觉下降 90%
- 支持复杂多跳推理

**关键纪律**：
- ✅ 双格式宪法：ttl 和 json 同源互校
- ✅ 七道闸门：宁可拒绝，不可污染

---

### 6.3 Phase 3：持续进化（长期）

**目标**：解决时效性幻觉 + 持续发现新幻觉模式

**行动**：
1. 上线完备性闸门
2. 建立查询轨迹记录机制
3. 实施进化治理层（六步循环）
4. 定期人工抽检（每批 20 条，精度 ≥ 80%）

**预期效果**：
- 本体持续进化，越用越准
- 同一个坑不踩两次
- 幻觉率持续下降

**关键纪律**：
- ✅ 三条铁律：没过验证不发布 / 验证用新问题 / 输了不发布
- ✅ 补丁回流：进化产出的补丁重新过闸

## 总结

**结构化本体解决模型幻觉的核心逻辑**：

1. **为什么能解决**：本体通过证据锚定、约束锁定、口径统一、路径推理四个机制，把 LLM 的概率输出收窄为确定性回答
2. **怎么解决**：五层防幻觉架构（知识原料 → 本体建模 → 知识蒸馏 → 完备性闸门 → 进化治理）层层过滤，持续修补
3. **效果如何**：幻觉率下降 50-90%，用户满意度提升 55%，Token 成本节省 20%
4. **边界在哪**：本体解决不了常识性、时效性、开放性、创造性幻觉，需要 RAG、进化治理、完备性闸门等补充
5. **如何落地**：分三阶段（快速见效 → 系统化 → 持续进化），先把 v0 建起来就值回票价

**核心观点**：模型是租来的，语义资产是自己的。本体不是技术目标，是业务问题逼出来的。有持续的问题流 + 有重复答错的模式，才值得建本体。
