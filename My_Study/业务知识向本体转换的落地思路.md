## 0. 核心命题：为什么必须做本体转换

### 对比：未接本体 vs 已接本体

**未接本体 — 裸 LLM 回答「退款率」**
- 百科式泛答：行业通用公式 + 罗列各种口径 + 口径陷阱提醒
- 通篇没有一句是"我们公司"的事实
- **模型是租来的，知识没留下来**

**已接本体 — 同一问题**
- 公司式确答：官方口径「售后退款成功订单数 ÷ 总订单数（自然月）」
- 取数位置 `aftersale.status='REFUND_SUCCESS'`
- 证据《产品手册 v3.2》§4.1
- 主动提醒"退货率≠退款率"
- **语义资产是自己的**

> **核心判断**：有持续的问题流 + 有重复答错的模式，才值得建本体。本体不是技术目标，是业务问题逼出来的。

## 1. 四层能力栈 + 工作区服务映射

### 架构层次与服务对应

| 能力层 | 解决的问题 | 工作区对应服务 |
|--------|-----------|---------------|
| **① RAG 层** | 答案在资料里但找不回来 | **WeKnora**（混合检索 + 重排 + 出处引用） |
| **② Ontology 层** | 同一业务对象在多系统含义/编号对不上 | **evoontology** + **schema.ttl/json** |
| **③ GraphRAG + Wiki 层** | 单篇能找到但跨文档连不起来 | **GBrain**（实体关系图谱 + Markdown 知识页） |
| **④ 查询编排层** | 规则在知识库里，订单状态在业务库里 | **SuperSonic**（语义层 + Text2SQL） |

### 各层覆盖场景

- **RAG 层**：制度问答、手册查询、客服查规则
- **Ontology 层**：术语消歧、口径统一、关系白名单、domain/range
- **GraphRAG + Wiki 层**：跨文档事实链接、决策历史追溯、知识沉淀
- **查询编排层**：业务看数、指标查询、报表生成

> **关键原则**：缺哪种能力补哪层，不是固定升级顺序。项目不缺的能力就不用为了凑齐架构再做一遍。先 RAG 解决 80% 的问题，再按需向上叠加。

### 知识源 → 本体构件映射规则

| 知识源 | 抽取目标 | → 本体构件 | 云帆实例 |
|--------|---------|-----------|---------|
| 产品手册 | 名词性概念 | 术语/类 (owl:Class) | SPU、SKU、售后单、订单 |
| 产品手册 | 关联动词 | 关系 (owl:ObjectProperty) | belongsToSpu、inCategory |
| SOP/制度文件 | "必须/不能"规则 | 约束 (Constraint) | 退款≤15天、生鲜仅质量退货 |
| 任意文档 | 出处定位 | 证据 (Evidence) | 《手册v3.2》§2.2 原文 |
| qa_log 问答日志 | 高频问题主语 | 术语优先级排序 | "待支付订单多久关闭"→订单域优先 |
| 数据字典 | 字段口径 | 属性 (DataProperty) | netWeightKg、价格、毛利率 |

### 输入层三件套

1. **人写的术语表**
   - 定义句式统一：上位类 + 区分特征 + 区别于易混词
   - 例：「售后单：售后域中买家发起退款请求的最小记录单元；区别于订单——订单是交易行为」

2. **存量业务文档**
   - LLM 从中蒸馏知识
   - evidence 必须抄原文片段，不转述
   - temperature=0 关掉随机性

3. **问答日志 qa_log**
   - 定域蒸馏：高频问题决定优先蒸馏哪个域
   - 围绕真实问题流构建，不从目录全量归纳

## 3. 转化核心：本体四件套建模法

### 将业务知识拆解为四种结构化构件

| 构件 | 定义 | 云帆商城实例 | 从知识源抽取的方法 |
|------|------|-------------|-------------------|
| **术语 Term** | 概念节点 | SPU、SKU、售后单、订单、优惠券、类目 | 从产品手册、FAQ 中抽取**名词性概念**；定义句式统一为「上位类 + 区分特征 + 区别于易混词」 |
| **关系 Relation** | 带方向的边，必须走白名单 | belongsToSpu(SKU→SPU)、inCategory(SPU→类目)、SAME_AS、PAIRS_WITH、SUBSTITUTES_FOR | 从文档中描述概念间关联的**动词短语**抽取；白名单把开放作文改选择题 |
| **约束 Constraint** | 不能违反的业务规则 | 「退款申请须在订单完成后15天内发起」「生鲜类目仅支持质量退货」「待支付30分钟自动关闭」 | 从制度文件、政策条款中**「必须/不能/仅限」**类表述抽取 |
| **证据 Evidence** | 知识的出处（最关键） | 「15天」→《产品手册 v3.2》§2.2 原文；「幂等键」→ RETRO-2026-09 复盘 | 每条知识**必须指回原文段落，抄原文而非转述**；没有证据的知识 = 模型编造的知识 |

### 判断口诀：纸面术语 → 机器格式

```
名词         → 类 (owl:Class)
能填格子的数  → 属性 (DataProperty)
动词         → 关系 (ObjectProperty)
说"必须/不能" → 约束 (Constraint)
```

### 教学示例：mini.ttl（9 条三元组）

```turtle
# 云帆商城商品域本体（教学版）
@prefix ex:   <http://example.com/ecom#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

# ---- 类 Class（3 个）----
ex:SPU      a owl:Class .
ex:SKU      a owl:Class .
ex:Category a owl:Class .

# ---- 关系（2 个，domain/range 对齐术语表）----
ex:belongsToSpu a owl:ObjectProperty ;
    rdfs:domain ex:SKU ;    # 出发端类型
    rdfs:range  ex:SPU .    # 到达端类型

ex:inCategory a owl:ObjectProperty ;
    rdfs:domain ex:SPU ;
    rdfs:range  ex:Category .
```

> **铁律**：没有证据的知识，与模型编造的知识无法区分。

## 4. 双格式宪法：schema.ttl + schema.json

### ttl 管语义声明，json 管数据校验

| 格式 | 职责 | 使用者 |
|------|------|--------|
| **schema.ttl**（语义层） | 机器可读的语义声明，定义类、关系、domain/range | 图数据库、推理引擎 |
| **schema.json**（校验层） | 数据落库前的结构校验，CSV/JSON 必须过这里的校验 | ETL 管道、应用代码 |

### 一致性锚点示例

| 锚点 | ttl 侧 | json 侧 | 一致性校验 |
|------|--------|---------|-----------|
| 类目 | ex:Category + inCategory 的 range | category: enum [8 个类目] | 英文键一字不差 |
| 商品状态 | "下架"消歧为两个术语 | status: enum [在售/预售/展示域下架/库存域下架] | 两个取值分别登记 |
| 净重 | netWeightKg 浮点属性 | "type": "number", minimum: 0 | "110码"被类型校验拦截 |
| SPU 编号 | ex:SPU 类 | spuId: pattern "^SP[0-9]{4,}$" | 正则与类声明对齐 |

> **铁律**：英文键一字不差。ttl 与 json 是同一套命名，改一处必须同步另一处。check_ttl.py 退出码 0 之前都算草稿。

## 5. 七道闸门：候选知识入库的质量流水线

### 「宁可拒绝，不可污染」—— 全机器执行，人只看日报

```
G1 JSON合法 → G2 白名单 → G3 实体对齐 → G4 属性归一 → G5 去重 → G6 冲突检测 → G7 置信分级
```

### 各闸门详解

| 闸门 | 拦截对象 | 云帆实例 | 异常信号 → 动作 |
|------|---------|---------|----------------|
| **G1** | LLM 输出解析失败 | JSON 格式不合法 | G1 高 → 改抽取 prompt |
| **G2** | AI 自创关系（头号 bug） | LLM 发明「升级为」关系 → 不在白名单 [sameAs, pairsWith, substitutesFor...] → 拦截 | G2 高 → 改抽取 prompt 的白名单提示 |
| **G3** | 两端实体不在术语表 | Apple / APPLE / apple 品牌多写法 → 四级对齐：规范化→别名表→相似度候选→**新建待确认（绝不自动合并）** | G3 高 → 对口径、补别名表 |
| **G4** | 单位/格式混乱 | 1.5L 与 1500ml 表达同一容量 → 按字典换算归一 | 补单位换算表 |
| **G5** | 重复三元组 | 同键不同证据 = 补充来源，不算重复 | — |
| **G6** | 同主谓不同宾 | 「30分钟 vs 大促60分钟」→ 三分法：时效冲突/条件冲突/真冲突 | G6 高 = 文档本身有矛盾 → 提交裁决 |
| **G7** | 低置信候选 | 宁延迟，不脏库 | 进待确认队列 |

### 质量日报 = 免费体检

- 每道闸的拦截率自动记录
- 哪个数字异常就修哪一层，不用等用户投诉
- 被拦 ≠ 判死刑，进待确认队列，人裁决通过后也要重新过闸

## 6. 落地路线图：从 0 到 1 三阶段实施

### Phase 1：v0 静态本体（30 天）🔵 人工主导

**1.1 术语表初建**
- 从产品手册 v3.2 + FAQ 中抽取核心名词：SPU、SKU、订单、售后单、优惠券、类目、品牌...
- 人工定义句式统一

**1.2 白名单关系定义**
- 先定 4-6 种核心关系：belongsToSpu、inCategory、BRAND_OF、SAME_AS、PAIRS_WITH、SUBSTITUTES_FOR

**1.3 双格式宪法落地**
- schema.ttl（语义层）+ schema.json（校验层）同源编写
- check_ttl.py 自动校验

**1.4 核心 10-20 个 Object Type 人工建模**
- 参考 Palantir 对标：商品(SKU)、用户、订单、优惠券、仓库、物流单、客诉工单

> **关键产出**：初始静态字典已贡献大部分收益——先把 v0 建起来就值回票价。实验数据：任务轮次 14.6→8.4，token 成本约 -20%。

---

### Phase 2：LLM 批量抽取 + 闸门校验（30 天）🟢 机器主导 + 人校验

**2.1 LLM 知识蒸馏**
- qa_log 定域 → 针对高频域文档做 LLM 蒸馏 → 产出 candidates.jsonl（候选池）
- 纪律：temperature=0、evidence 抄原文、每批 20 条

**2.2 七道闸门上线**
- 参考 m5_extract_demo.py 的五道闸实现，扩展到七道
- 拦截率自动记录为质量日报

**2.3 图数据库导入**
- 参考 graph_import.py：Neo4j MERGE 语义（有则复用无则建）
- 对账口径 SPU=12/Brand=8/Category=8/关系≥32

**2.4 人工抽检**
- 每批固定 seed 抽 20 条，精度 ≥ 80% 才收批
- 抽检对/错/存疑三档，「对」必须有出处

---

### Phase 3：聚类补盲区 + Action 注入 + 进化闭环（30 天）🟡 持续运营

**3.1 查询轨迹收集**
- 使用攒轨迹（30 任务/7 天触发）
- 找重复 miss 模式 → 诊断归因（内容层/工具层/模式层）

**3.2 单点补丁 + 同条件验证**
- 只改一处
- 用没参与建库的新问题验证
- 赢了才发布新版本，旧版永留可回滚

**3.3 Action Type 注入（Palantir 灵魂）**
- 自动补货、下架商品、发放优惠券、拆单改仓
- 让本体从「地图」升级为「可执行的操作手册」

**3.4 补丁回流**
- 进化产出的补丁不直接改库，回到候选池重新过七道闸
- 没有「进化豁免权」

> **三条铁律**：
> 1. 没过验证的改动不配正式版本号
> 2. 验证必须用没参与建库的问题
> 3. 同条件对比输了就不发布

## 7. 关键难点：消歧、冲突与数据体检

### 消歧实例 —— 「下架」的两种含义

**错误做法：先合并再拆**
```
"下架" → 一个术语
↓ 积累关系和证据
↓ 发现有两种含义
↓ 试图拆分
→ 两团知识焊死，不可逆
```

**正确做法：先分清后合并**
```
"下架" → 展示域下架 + 库存域下架
↓ 各自建关系和证据
↓ 用一阵子确认边界
↓ 确认同义才合并
→ 可控、可逆、可追溯
```

> **铁律**：「先分清后合并」是铁律。反着来就完了——先合并再拆→两团知识焊死在一起，不可逆操作。

---

### 冲突检测实例 —— G6 三分法

| 冲突类型 | 云帆实例 | 处理方式 |
|---------|---------|---------|
| **时效冲突** | 「待支付 30 分钟自动关闭」vs「大促延长至 60 分钟」 | 把「大促期间」登记为条件维度，两条规则并存 |
| **条件冲突** | 「7天无理由」vs「美妆拆封不支持」vs「生鲜仅质量退货」 | 按类目分条件，各规则在各自条件下成立 |
| **真冲突** | 同一文档前后矛盾 | 人裁决 → 裁决写回 → 旧口径存档可回滚 |

## 9. 智能问数落地：本体如何服务于可信查询

### 「AI 只住一个笼子」—— 五层架构

```
会话编排层（前台）：输入联想 · 会话记忆 · 澄清问答 · 结果组装
       ↓ 受限查询意图（含硬约束）
语义解析层（翻译段）：词典命中 → 规则轨+LLM轨双轨调度 → 校正器+完备性闸门
       ↓ DSL（受限中间语言）
语义层（心脏）：指标/维度/口径登记 · DSL→SQL编译器 · 权限注入 · 缓存
       ↓ 物理SQL
执行与数据层 + LLM基础设施
```

> **核心原则**：LLM 只负责翻译段。AI 产出的是**声明**（查什么），编译器产出**实现**（怎么查）。join、聚合、公式 AI 全程不碰物理表。

---

### 完备性闸门 —— 「宁可反问，不可降智」

| 检查类型 | 内容 |
|---------|------|
| **合法性检查** | 用的符号是否都在白名单内，对照 schema.ttl 的类/关系清单 |
| **完备性检查** | 用户问题里的条件逐一检查查询里有没有对应表达，缺了就拦截 → 反问用户补充 |

判定标准可配置：
- 用户点选过的硬约束 100% 必须落进查询
- 自然语言命中的 70% 须覆盖

---

### 双轨解析 —— 80% 流量走免费确定性

| 轨道 | 触发条件 | 成本 | 适用场景 |
|------|---------|------|---------|
| **规则轨（先跑）** | 命中预置问句模板 | 零 LLM 成本，秒回 | 「近 30 天订单量」「各类目销售额」等标准句式 |
| **LLM 轨（补位）** | 规则接不住的复杂问法 | 有 token 成本 | 「卖得最贵的保温杯在哪个仓库」「A 品牌搭配 B 类目的退货率」 |

> **业务事实**：80% 的问数流量是标准句式——让免费确定性的规则吃大头。

## 10. 人机分工与治理体系

### 四阶段人机协作矩阵

| 阶段 | 人主导 | 机器主导 | 协作方式 |
|------|--------|---------|---------|
| **① 输入层** | ✓ 人写术语表和 schema | | 人定标准，机器执行 |
| **② 闸门链** | | ✓ 七道闸按序跑 | 人只看质量日报 |
| **③ 存储+查询** | 人设计 | 机器跑 | 人设计架构，机器执行查询 |
| **④ 进化+治理** | 人裁决冲突 | 机器记录轨迹 | 发布决定权始终在人手里 |

---

### 治理闭环

```
口径争议 → 提交评审 → 裁决写回 → 补丁回灌 → 验证通过 → 发布新版 → 沉淀系统
   ↓          ↓          ↓          ↓          ↓          ↓          ↓
发现不一致  进入裁决队列  旧版存档   重新过闸   用新问题测试  版本号+1   同一架不吵第二次
```

> **铁律**：吵完的结论沉淀进系统——同一个架不用吵第二次。发布决定权始终在人手里。

---

### 三条铁律总结

1. **没过验证的改动，永远不配正式版本号** —— 版本号是质量认证，不是时间戳
2. **验证必须用没参与建库的问题** —— 拿课本例题考学生，什么都没证明
3. **同条件对比，输了就不发布** —— 涨1分可能只是随机波动，分数差距要可复现

## 附录：关键方法论总结

### 核心转化原则

1. **证据是可信的根** —— 每条知识必须指回原文段落
2. **按需查询，不是全量注入** —— 用到哪个查哪个
3. **白名单和 domain/range 是机器能执行的纪律** —— 牺牲表达自由换系统可控
4. **宁可拒绝不可污染** —— 被拦不等于判死刑
5. **赢了才发布，版本永不覆盖** —— 进化在人监督下进行
6. **经验是公共的，本体是你自己的** —— 业务知识是差异化资产

### 选型判断

- **该不该建本体**：有持续的问题流 + 有重复答错的模式，才值得建
- **LLM Wiki vs Ontology**：先问业务走到哪一步——LLM Wiki 先做，需求升级再上 Ontology，两阶段是接力关系
- **Text2SQL vs Text2Metrics**：探索期 SQL 自由，生产期 Metrics 纪律

### 效果数据参考

- 开放研究型任务提升 +20 分
- Text2SQL +8.8 分
- 标准分析型只 +1 分
- 任务轮次 14.6 → 8.4
- token 成本约 -20%
- 初始静态字典已贡献大部分收益——先把 v0 建起来就值回票价
- Palantir 对标：同一任务（流失用户分层发券），数据中台方案 4 天 vs 本体架构 2 小时
